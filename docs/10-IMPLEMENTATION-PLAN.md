# Implementation sequence for the coding agent

This sequence begins only after the user instructs a coding agent to build. The documentation phase has created no application files or installed packages.

## Phase 1 — Inspect and establish the baseline

Read the handoff and source evidence, inspect the actual repository and any applicable instructions, identify existing stack/assets, and map every REQ ID to the intended route. Reuse a sound existing stack; otherwise follow the proposed architecture. Resolve supported versions from official documentation and lock them. Define preview versus production configuration before adding data capture.

Deliverable: working project baseline, routing skeleton, content types, publication rules, and a concise implementation decision record. Do not buy services or invent credentials.

## Phase 2 — Build complete static information first

Implement header/footer, every required page, all 24 service entries, exact source booking copy, package placeholders with explicit private-preview provenance, three customer steps, four creator steps, and both form layouts.

Use honest placeholders for missing real media/reviews. Finish mobile layout and accessible controls before adding complex motion. Keep the initial site informative with scripts disabled where possible.

Deliverable: a coherent, navigable preview that fully reflects the content scope. It may be commercially incomplete because source facts are missing; those gaps must be visible to the owner in preview.

## Phase 3 — Create durable intake

Implement database migrations, request validation, idempotent enquiry/application submissions, outbox notifications, private upload sessions, size/type inspection, attachment rules, and cleanup. Wire an operator-approved back-office path; a custom admin dashboard is not required.

Develop against local/test resources. Do not enable public collection while notice, access, retention, storage, device rules, or notification destination remain unresolved. A no-provider demo must explicitly identify itself and cannot pass functional acceptance.

Deliverable: both end-to-end flows store data reliably and survive failure/retry scenarios in the configured test environment.

## Phase 4 — Produce the visual story

Select/prepare approved hero and portfolio assets using the asset brief. Build the opening composition and matching reel reveal. Extend the three service moods using the shared palette, typography, spacing, and media treatment. Keep interior pages direct and practical.

Deliverable: the signature scene works as a complete still design and as optional motion. Real work is accurately labelled and playable. The mobile composition is intentionally designed rather than a scaled desktop screenshot.

## Phase 5 — Finalize source decisions

Use the decision register to collect specific owner answers. Update content data and record date/evidence for each answer. Do not request permission for every reversible design adjustment; typography, spacing, and implementation choices are delegated through this plan. Ask only for missing business facts, approved public assets, provider/destination details, and actual release authorization where needed.

Deliverable: every enabled public feature has its required information. If the owner defers something, record the exact change from the DOCX scope and reflect it consistently in navigation, metadata, and acceptance criteria.

## Phase 6 — Verify and prepare release

Run the checks in [quality and acceptance](09-QUALITY-AND-ACCEPTANCE.md). Inspect every route and actual form state, not just the home hero. Fix defects, retest changed behaviour, and provide a reviewable result with screenshots and a truthful report. Deployment itself is a separate action governed by the user's build/release instructions.

Deliverable: production-ready build if decisions/providers are resolved; otherwise a completed preview with precise launch blockers. Never represent an unconfigured or mocked submission as a live service.

## Milestone priority

**P0:** source fidelity, routes, real form persistence, private uploads, honest feedback, accessible mobile usability.

**P1:** approved media, cinematic hero, gallery, motion fallbacks, strong typography, refined comparison and workflow pages.

**P2:** optional analytics, extra media filters, additional decorative scene detail. These must not delay or replace P0/P1.

## Work not included

Instant availability, payments, discounts, customer login, creator login, live matching, GPS tracking, shoot PINs, workshop booking, payouts, customer delivery portal, native app, custom CRM, blog, and multilingual expansion. Do not build any of these because they appear in another brand's reference image.

## Suggested initial prompt for the future coding agent

> Build The Reel Wala website using this repository's documentation pack. Start with docs/00-START-HERE.md, follow the source precedence in docs/01-REQUIREMENTS.md, and implement the original story and palette specified in docs/02-STORY-AND-ART-DIRECTION.md and docs/03-DESIGN-SYSTEM.md. Preserve all required pages, all 24 service entries, the Workflow-page enquiry form, and the creator requirements. Use the architecture and API contracts, and distinguish confirmed source values from reference-only or unresolved business facts. Build a complete private preview while keeping unapproved claims out of production. Do not fabricate prices, testimonials, locations, eligibility, or operational promises. Verify real persistence, uploads, accessibility, desktop/mobile layouts, and failure states against docs/09-QUALITY-AND-ACCEPTANCE.md. Report exactly what works and which owner decisions still block public release.

## Completion report template

Report implemented routes and source requirements; chosen stack/provider decisions; approved versus missing assets; real versus demo integrations; tests and viewports checked; accessibility/performance findings; unresolved decision IDs; and how to run/review the build. Include evidence, not blanket statements such as “fully production-ready” when dependencies are absent.
